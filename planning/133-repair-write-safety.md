# 133 — Repair-Write Safety

**Status:** decided — keep both repair paths, with different jobs.
**Scope:** the two writes that touch a launcher's own folders. `data/` writes are the persistence
contract (`132`).

---

## 1. The distinction that decides the design

| | Steam ACF | Epic `.item` |
|---|---|---|
| Format | fully known, fully generated (`SteamAcfWriter.Build`) | not generated by us; Epic writes it |
| Legitimate action | **create** `appmanifest_<appId>.acf` for an existing folder | **modify** an `.item` Epic already wrote, after the user moved the files |
| Target absent | normal case | refuse — we cannot invent a valid item |
| Target present | refuse (never overwrite) | the only case that runs |
| Failure safety | delete the file we just created | restore the backup of the file we replaced |

Both stay. An earlier draft removed the Epic writer on the grounds that it cannot create a valid item;
that was the wrong conclusion — modifying an existing item is exactly ADR-005's "Fix Registration" and is
worth keeping. What must go is the *creation* and *hollow-replacement* behaviour.

## 2. Evidence

### Steam ACF writer

| Item | Location |
|---|---|
| `TryWrite` | `App/Services/SteamAcfWriter.cs:39` |
| target | `:61-72` — `<libraryRoot>\steamapps\appmanifest_<appId>.acf` |
| directory creation | `:64` — `Directory.CreateDirectory(steamapps)` |
| preflight | `:49` AppID digits, `:55` root/installdir non-empty, `:73` refuse if file exists |
| write | `:81` — `File.WriteAllText(path, Build(...))` |
| UI entry | `MainWindow.PlatformRepair.cs:76` (button `MainWindow.axaml:151`) |

Never overwrites today. The defects are the directory creation and the in-place truncating write.

### Epic `.item` writer

| Item | Location |
|---|---|
| `TryWrite` | `App/Services/EpicItemWriter.cs:9` |
| directory creation | `:65` — `Directory.CreateDirectory(manifestsDir)` |
| target | `:73` — `<manifestsDir>\<installationGuid>.item` |
| create-or-replace | `:74-78` + `IsHollowItem` `:157-171` |
| write | `:143-148` — full known-schema JSON replaces the file |
| UI entry | `MainWindow.PlatformRepair.cs:18` (button `MainWindow.axaml:156`, dialog `EpicRepairDialog.cs`) |
| manifests dir | `EpicManifestParser.cs:287-300` — `%ProgramData%\Epic\EpicGamesLauncher\Data\Manifests`, overridable by `EPIC_MANIFESTS_DIR` |

Defects to remove:

1. It creates the manifests folder when absent (`:65`), i.e. fabricates a launcher directory.
2. `IsHollowItem` returns `true` on a parse failure (`:167-170`), so a corrupt `.item` is overwritten with
   our payload. A file we cannot read is not a file we may replace.
3. It rewrites the whole item from our fixed schema, discarding any member Epic wrote that we do not know
   about — the opposite of a minimal registration update.
4. It writes the item when none exists, which cannot produce a valid registration.

## 3. Shared contract

Applies to both writers. Everything here is one safeguard per failure class, not layers.

### 3.1 Preflight — no writes, no directory creation

1. Reject a relative path, a UNC path, and a path that is not rooted (`Path.IsPathRooted`).
2. `Directory.Exists(targetDir)` — false → refuse, name the expected path, and **do not create it**.
3. Store marker (see §3.2) — false → refuse.
4. Target presence rule (see §3.2).
5. No `Directory.CreateDirectory` outside the application data root. `data/staging/` and
   `data/backups/` come from `AppPaths.EnsureAppDataPath` (`132`).

### 3.2 Per-store preconditions

| | Steam | Epic |
|---|---|---|
| target dir | `<libraryRoot>\steamapps` | `<manifestsDir>` |
| marker | `libraryfolders.vdf` exists | the dir is the manifests dir the scan used, and it contains at least one other `*.item` |
| target | `<steamapps>\appmanifest_<appId>.acf` **must be absent** | `<manifestsDir>\<guid>.item` **must exist and parse** |
| also required | AppID digits, non-empty installdir | `InstallationGuid`, `InstallLocation`, `CatalogNamespace`, `CatalogItemId` present |

A corrupt or unreadable `.item` is a refusal (`"cannot read item; nothing was written"`), never a replace.
The old "hollow item" branch is deleted.

### 3.3 Generate, prove, copy

1. Build the payload in memory.
   - Steam: `SteamAcfWriter.Build`.
   - Epic: parse the existing file as a `JsonNode`, set only the members we own (`InstallLocation`,
     `ManifestLocation`, and `LaunchExecutable` when it is empty), leave every other member untouched.
2. Validate in memory: re-parse the string; Steam checks AppID/name/installdir; Epic checks the four
   required members and that the unknown members are still present (compare member count before/after).
3. Write the bytes to `data/staging/<name>` and read that file back, parsing it again. The bytes that
   will be copied are the bytes proven.
4. Back up, Epic only: `File.Copy(target, data/backups/<utc-stamp>/<guid>.item)`. Create the backup
   directory through `AppPaths`, and refuse the write if the backup cannot be made.
5. `File.Copy(staged, target)` — one call.
6. Compare `new FileInfo(target).Length` with the staged length. Mismatch:
   - Steam → delete the target (it did not exist before);
   - Epic → restore the backup over the target.
7. `IOException`/failure after step 4:
   - Steam → delete a zero-length or wrong-length target if one exists;
   - Epic → restore the backup.
8. Delete the staged file in `finally`. Nothing else is written to the store folder — no temp file, no
   rename, no second pass.

### 3.4 Journal and dry run

- `data/repair-journal.jsonl`, one line per attempt: timestamp, action (`steam-acf` / `epic-item`),
  target, backup path (Epic), staged length, final length, outcome (`ok`/`refused`/`failed`), message.
  Refusals are included.
- Dry run returns target, backup location, payload length, and validation result; writes and creates
  nothing.
- The confirmation shows target path, payload size, the marker that validated the folder, and for Epic the
  backup location.

### 3.5 Validation is length plus a successful parse

No hash, digest, signature, or chain. A digest written by the same process into the same folder with the
same permissions verifies nothing. For Epic, the preserved member count is what proves we modified rather
than replaced the item.

### 3.6 Backups

- One backup per Epic modification, under `data/backups/<utc-stamp>/`, kept (ADR-005 reversibility).
- No backup for Steam, because the target never existed.
- No restore command in this change: restore is copying the backup back by hand, and the journal names the
  path. A restore action would be a third write path for a problem a file copy already solves.

## 4. Per-store paths and the gate

Unique per-store code is expected and correct: Steam and Epic do not share a locator, a manifest format,
or a target rule. What must not be duplicated is the *rule* — target validation, the no-create rule, the
staging sequence, the journal. Those live in one helper used by both writers; each writer supplies only
its own target derivation and preconditions.

Which path runs is decided by the entry's `GameSourceKind` and the user's action, not by sniffing folders
at write time:

```
action (repair) + GameSourceKind
    ├─ Steam → SteamAcfWriter   (create, marker: libraryfolders.vdf)
    ├─ Epic  → EpicItemWriter   (modify, marker: manifests dir + existing item)
    └─ other → no repair action
```

That table is the map the next section requires; today only the two writers and their two callers exist.

---

## 5. Windows facts

- `File.WriteAllText`, `File.Copy`, and `File.Move` do not create parent directories; they throw
  `DirectoryNotFoundException`. A `CreateDirectory` frame in ProcMon is an explicit API call.
- `File.WriteAllText` uses `FileMode.Create`; `File.Copy(overwrite: true)` truncates the destination. An
  interrupted write leaves a short file, which is why the length check exists.
- `%ProgramData%` is writable by an elevated process, not by a standard user. Creating the Epic manifests
  folder would fail on a locked-down machine anyway; refusing is both safer and more accurate.
- A file being read by Epic at the same moment can be replaced on NTFS but Epic may rewrite it; the dialog
  already tells the user to quit Epic first.

## 6. Test matrix

| Case | Steam | Epic |
|---|---|---|
| target dir missing | refused, dir still absent | refused, dir still absent |
| marker missing | refused (`libraryfolders.vdf`) | refused (dir is not the scan's manifests dir) |
| target absent | **written**, parses, length matches, staging removed | refused ("cannot create; Epic writes it") |
| target exists | refused, bytes unchanged | **modified**, `InstallLocation` updated, all other members byte-preserved, backup exists |
| target corrupt | n/a (absent rule) | refused, bytes unchanged, no backup taken |
| read-only target dir | failed, no target left behind | failed, original restored, journalled |
| interrupted copy | target deleted, failed | backup restored, failed |
| relative / UNC path | refused before any filesystem call | refused before any filesystem call |
| dry run | target reported, filesystem unchanged | target + backup reported, filesystem unchanged |

Tests use temp directories owned by the test, so they run on the Linux host. No test may depend on a real
Steam or Epic installation. The Steam tests need `libraryfolders.vdf`; the Epic tests need a synthetic
`.item` with one unknown member to prove preservation.

## 7. ADR and follow-ups

- **Proposed ADR-005 amendment (for human approval):** repair writes are split by ability. Create when the
  format is fully known and the target is absent; modify only when the launcher's own file exists, with a
  backup and an untouched-unknown-members check. Never create a launcher-owned directory.
- Contract accuracy: `GamingCommander.Readme.txt:256-260` says `data/` is the only folder written to; it
  must name the two repair writes. `docs/FAQ.md:138` already covers the Steam case and needs the Epic
  modify case.
- The per-store decision tree and its failure points are the connection map's job; until that exists, §4 is
  the whole map.
- A future "update an existing ACF" repair (cross-library or installdir correction) is a **modify** path,
  not this create path. It needs its own preconditions, a backup, and a restore rule before it is exposed;
  the deferred SyncMove task is the recorded consumer.
- `EpicItemWriter` is the only writer that replaces a launcher-owned file today. If a second replace path
  appears, the backup/restore rules here are the template, not a new invention.
